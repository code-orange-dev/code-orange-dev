# Privacy Contributor Scorecard

This scorecard measures contributor development, not course completion.

## Competency levels

| Level | Description |
|---|---|
| 0 — Observing | Can follow guided exercises but cannot yet work independently. |
| 1 — Assisted | Can complete tasks with explicit instructions and mentor support. |
| 2 — Contributor-ready | Can independently build, navigate, test and communicate around scoped work. |
| 3 — Independent contributor | Identifies and completes useful work with normal upstream feedback. |
| 4 — Trusted contributor | Provides reliable reviews, handles ambiguous work, and is recognized by upstream collaborators. |
| 5 — Multiplier | Maintains/reviews regularly and helps other contributors become effective. |

## Assessment dimensions

### Protocol and privacy reasoning
Evidence: threat models, protocol explanations, privacy analyses, design discussions.

### Codebase comprehension
Evidence: code walkthroughs, subsystem maps, historical PR/issue analysis, ability to locate relevant code without step-by-step direction.

### Build and testing
Evidence: reproducible builds, PR test reports, bug reproduction, added tests, fuzzing, benchmarks, regression identification.

### Review
Evidence: review notes, upstream review comments, identification of edge cases/missing tests, conceptual review, follow-up discussion.

### Authored contributions
Evidence: patches, PRs, tests, refactors, fixes, documentation and other accepted changes. Complexity/usefulness is considered separately from count.

### Issue work
Evidence: triage, reproduction, clarification, root-cause investigation, issue resolution.

### Technical communication
Evidence: clear issue/PR descriptions, constructive review discussion, responsiveness to feedback, ability to explain trade-offs.

### Independence
Evidence: finding useful work, scoping tasks, seeking context, resolving blockers and engaging upstream without mentor orchestration.

### Collaboration
Evidence: reviewing peers, helping cohort members, sharing debugging context, supporting Review Club.

### Upstream relationship
Evidence: repeat interactions, maintainer feedback, invitations to continue work, increasing responsibility.

### Continuity
Evidence: meaningful project activity at 3, 6 and 12 months.

### Community multiplier
Evidence: mentoring, Review Club facilitation, documentation for newcomers, teaching, maintainer responsibilities.

## Contribution record

Each meaningful activity should record:

- date;
- participant;
- upstream project;
- contribution type;
- URL/evidence;
- short description;
- competency dimension(s);
- mentor assessment where relevant;
- upstream response/status;
- follow-up action.

## Contribution types

Use explicit types rather than treating everything as a PR:

- CODE_AUTHORSHIP
- CODE_REVIEW
- TESTING_VALIDATION
- ISSUE_INVESTIGATION
- TEST_FUZZ_BENCHMARK
- DOCUMENTATION
- PROTOCOL_RESEARCH
- TECHNICAL_DISCUSSION
- PEER_SUPPORT
- MAINTENANCE

## Quality rubric

Where qualitative assessment is useful, contributions can be tagged:

- **Exploratory** — useful primarily for learning/context gathering.
- **Useful** — provides real information or improvement to the project.
- **Substantive** — materially advances an issue, review, design, test, or implementation.
- **Trusted** — demonstrates judgment/ownership expected from a recurring project contributor.

These tags are not points. They help mentors discuss growth without encouraging gaming.

## Graduation / residency-readiness indicators

A participant is ready for independent residency when they can demonstrate most of the following without step-by-step instruction:

- build and run the target project;
- navigate relevant code and tests;
- explain a real issue and its context;
- test an upstream PR and communicate useful results;
- provide at least one meaningful review contribution;
- respond constructively to technical feedback;
- scope a small contribution;
- identify at least one useful piece of work from upstream priorities;
- explain privacy/security trade-offs relevant to their work.

## Fellowship selection indicators

Fellowship selection should emphasize:

1. sustained engagement with one project;
2. evidence of useful review/testing, not only authorship;
3. increasing technical difficulty;
4. reliability and communication;
5. ability to work through ambiguity;
6. upstream feedback;
7. initiative and independence;
8. clear 3–6 month contribution plan;
9. likelihood that funding materially increases sustained OSS contribution.

PR count is supporting evidence, never the primary ranking mechanism.
